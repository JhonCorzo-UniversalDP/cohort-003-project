  How the Frontend Technologies Interact

  Think of it as a layered stack where each technology has a clear role:

  User sees the page
         │
         ▼
  ┌─────────────────────────────────────────────────┐
  │  React (v19) — Component tree, state, rendering │
  │    ├── React Router v7 — SSR, loaders, actions  │
  │    │     └── Zod — validates form/param data     │
  │    │         inside loaders and actions           │
  │    ├── shadcn/ui + Radix UI — Pre-built UI       │
  │    │     └── Tailwind CSS — all styling           │
  │    ├── Monaco Editor — rich markdown editing      │
  │    └── Lucide React — icons                      │
  └─────────────────────────────────────────────────┘
         │
         ▼ (server-side only)
  ┌─────────────────────────────────────────────────┐
  │  marked — converts markdown to HTML              │
  │    └── Shiki — syntax-highlights code blocks     │
  └─────────────────────────────────────────────────┘

  React is the foundation — everything renders as React components. React Router
   v7 sits on top and controls the full request lifecycle: its loader functions
  fetch data server-side, and action functions handle form submissions. Tailwind
   CSS provides all styling — you won't find CSS files or styled-components,
  just utility classes. shadcn/ui provides pre-built components (buttons, cards,
   tabs, etc.) built on top of Radix UI primitives, all styled with Tailwind.
  Lucide React supplies the icons.

  The key interaction point is inside route files — that's where all these
  technologies converge. A single route file like instructor.new.tsx will:
  - Use Zod in the action to validate the form submission
  - Use shadcn/ui components for the form inputs and layout
  - Use Tailwind classes for spacing and styling
  - Use React Router hooks (useActionData, useNavigation) for form state

  Deep Dive on the Three Technologies

  Zod Validation

  Zod is a schema declaration and validation library. In Cadence, it's the
  gatekeeper between user input and the backend. It's used in 19 route files —
  essentially every route that accepts input.

  The project centralizes its Zod patterns in app/lib/validation.ts, which
  provides three helpers:

  - parseFormData(formData, schema) — takes raw FormData from a form submission,
   validates it against a Zod schema, and returns either the typed data or a
  field-error map. Used in action functions.
  - parseParams(params, schema) — validates URL params (like :courseId). Throws
  a 400 if invalid.
  - parseJsonBody(request, schema) — validates JSON request bodies from API
  endpoints.

  A typical usage in a route looks like:
  // Define shape
  const newCourseSchema = z.object({
    title: z.string().trim().min(1, "Title is required."),
    description: z.string().trim().min(1, "Description is required."),
    ...
  });

  // Validate in the action
  const parsed = parseFormData(formData, newCourseSchema);
  if (!parsed.success) return data({ errors: parsed.errors }, { status: 400 });

  Monaco Editor

  Monaco is the same editor engine that powers VS Code, embedded in the browser.
   In Cadence, it's used for one specific purpose: instructors editing lesson 
  content in Markdown.

  The implementation lives in app/components/monaco-markdown-editor.tsx. Key
  details:

  - Lazy loaded — it's a heavy library (~2MB), so it's dynamically imported with
   import("@monaco-editor/react") only when needed, showing an empty placeholder
   while loading
  - Custom theme — defines a "cadence-dark" theme that matches the app's dark UI
  - Prettier integration — registers Prettier as the document formatter for
  Markdown, so Ctrl+S formats the content before saving
  - Used by instructors only — it appears on lesson editing pages
  (instructor.$courseId.lessons.$lessonId.tsx)

  Students never see Monaco. They see the rendered markdown output instead.

  Shiki Syntax Highlighting

  Shiki is a syntax highlighter that produces pre-colored HTML (unlike
  client-side highlighters that run in the browser). In Cadence, it runs
  server-side only in app/lib/markdown.server.ts.

  The flow:
  1. Lesson content is stored as Markdown in the database
  2. When a student views a lesson, the server calls renderMarkdown(content)
  3. marked parses the Markdown into HTML
  4. For every code block (```typescript ... ```), Shiki takes over and produces
   syntax-highlighted HTML using the github-dark theme
  5. The pre-highlighted HTML is sent to the browser — no client-side JS needed
  for highlighting

  It supports 13 languages (TypeScript, JavaScript, JSON, Bash, HTML, CSS, TSX,
  JSX, SQL, YAML, Markdown, text, plaintext) and uses a singleton highlighter
  instance for performance.

  ---
  In summary: Monaco and Shiki handle two sides of the same coin — Monaco lets
  instructors write markdown with code blocks, and Shiki makes those code blocks
   look good when students read them. Zod is the validation layer that sits
  between every user action and the database.

  Schema at a Glance (14 tables)

  Core entities:
  - users — students, instructors, admins (distinguished by role enum)
  - categories — course groupings (e.g. "Programming")
  - courses — belongs to one instructor and one category; has status
  (draft/published/archived), price, and PPP toggle

  Course content (hierarchical):
  - modules — ordered sections within a course (position)
  - lessons — ordered items within a module; hold markdown content, videoUrl,
  and optional githubRepoUrl

  Student activity:
  - enrollments — links a user to a course (with optional completedAt)
  - lesson_progress — per-user, per-lesson status (not_started / in_progress /
  completed)
  - video_watch_events — granular tracking of play/pause/seek events with
  timestamp positions

  Commerce:
  - purchases — records payment amount and country (for PPP pricing)
  - coupons — redemption codes tied to a team purchase; each code is single-use
  (redeemedByUserId)

  Quizzes (4-table hierarchy):
  - quizzes → quiz_questions → quiz_options (the choices)
  - quiz_attempts → quiz_answers (records which option was selected per
  question)

  Teams:
  - teams + team_members — group users with admin/member roles; linked to
  coupons for bulk course access

  The main relationship chains to remember:
  - courses → modules → lessons → (quizzes, progress, video events)
  - users → enrollments → courses
  - teams → coupons → purchases

  How PPP Works

  PPP lets instructors offer discounted prices to users in lower-income
  countries, preventing VPN abuse by locking discounted purchases to the country
   they were bought in.

  1. Country Detection (app/lib/country.server.ts)

  Every request that needs pricing runs resolveCountry(request), which tries
  three sources in order:

  1. Dev session override  →  set via /api/set-dev-country (dev UI only)
  2. Cloudflare CF-IPCountry header  →  auto-populated in production by
  Cloudflare
  3. ip-api.com fallback  →  GeoIP lookup using X-Forwarded-For IP

  If all fail → returns null → treated as Tier 1 (full price).

  2. Tier System (app/lib/ppp.ts)

  Countries are hardcoded into 4 tiers:

  ┌──────┬─────────────────┬────────────────────────────────────────┐
  │ Tier │    Discount     │           Example countries            │
  ├──────┼─────────────────┼────────────────────────────────────────┤
  │ 1    │ 0% (full price) │ US, UK, DE, JP, SG                     │
  ├──────┼─────────────────┼────────────────────────────────────────┤
  │ 2    │ 30% off         │ Brazil, Mexico, Poland, Turkey         │
  ├──────┼─────────────────┼────────────────────────────────────────┤
  │ 3    │ 50% off         │ India, Colombia, South Africa, Vietnam │
  ├──────┼─────────────────┼────────────────────────────────────────┤
  │ 4    │ 70% off         │ Nigeria, Pakistan, Bangladesh, Egypt   │
  └──────┴─────────────────┴────────────────────────────────────────┘

  Any unlisted country defaults to Tier 1.

  3. Purchase Flow (app/routes/courses.$slug.purchase.tsx)

  At checkout:
  1. resolveCountry() detects the buyer's country
  2. calculatePppPrice(priceInCents, countryCode) applies the discount: price * 
  (1 - discount)
  3. The purchase record stores the country at time of purchase

  4. Access Control (checkPppAccess in ppp.ts)

  When a student tries to access a course they bought at a discount, the app
  checks:
  - Is the course paid and PPP-enabled? If not → allow
  - Was it a Tier 1 (full-price) purchase? → allow (no restriction)
  - Is the current country different from the purchase country? → block

  This prevents buying at 70% off in Nigeria and then accessing from Germany.

  How React Router v7 Works in This Project

  React Router v7 is a full-stack framework — it handles both the server and
  client. Think of it as Remix, because it effectively is (Remix was merged into
   React Router v7).

  The Setup Chain

  vite.config.ts
    └── reactRouter() plugin  ← turns Vite into a full-stack server
          └── app/routes.ts   ← central route registry
                └── app/root.tsx  ← top-level HTML shell
                      └── route files in app/routes/

  vite.config.ts has three plugins:
  - reactRouter() — the core plugin that enables SSR, loaders, and actions
  - tailwindcss() — Tailwind v4 via Vite plugin (no tailwind.config.js needed)
  - tsconfigPaths() — enables the ~/ alias (maps to app/) so you can write
  import { db } from "~/db" anywhere

  Route Registration (app/routes.ts)

  Routes are defined programmatically (not by file-system convention):

  export default [
    index("routes/home.tsx"),                          // GET /
    layout("routes/layout.app.tsx", [                  // shared layout wrapper
      route("dashboard", "routes/dashboard.tsx"),       // GET /dashboard
      route("courses/:slug", "routes/courses.$slug.tsx"), // GET 
  /courses/my-course
      ...
    ]),
    route("api/video-tracking", "routes/api.video-tracking.ts"), // POST 
  /api/video-tracking
  ] satisfies RouteConfig;

  The layout() call means all nested routes share the shell in layout.app.tsx
  (the sidebar, nav, etc.) without re-rendering it on navigation.

  Route File Anatomy

  Each route file can export up to three things:

  // 1. loader — runs SERVER-SIDE on GET, feeds data to the component
  export async function loader({ params, request }: Route.LoaderArgs) {
    const course = getCourseBySlug(params.slug);
    if (!course) throw data("Not found", { status: 404 });
    return { course };
  }

  // 2. action — runs SERVER-SIDE on form POST/PUT/DELETE
  export async function action({ request }: Route.ActionArgs) {
    const formData = await request.formData();
    // validate, mutate DB, redirect...
  }

  // 3. default export — the React component, receives loader data
  export default function CoursePage({ loaderData }: Route.ComponentProps) {
    const { course } = loaderData; // fully typed from loader return
    return <div>{course.title}</div>;
  }

  Type Safety

  React Router generates types automatically via pnpm typecheck (runs
  react-router typegen). The Route types imported at the top of each file (e.g.
  import type { Route } from "./+types/courses.$slug") are auto-generated,
  giving you end-to-end TypeScript safety from loader return → component props.

  root.tsx — The HTML Shell

  root.tsx is the outermost wrapper rendered for every request. It:
  - Outputs the full <html> document with <head> and <body>
  - Injects an inline script that sets dark mode before React hydrates (prevents
   flash)
  - Renders a top-of-page loading bar using useNavigation() during client-side
  navigations
  - Defines the global ErrorBoundary (404s, 500s) shown when any route throws
